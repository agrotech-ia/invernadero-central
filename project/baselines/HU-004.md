# HU-004 — Definir catálogo formal de roles, capacidades y matriz RACI

## 1. Información general

**ID:** HU-004
**Título:** Definir catálogo formal de roles, capacidades y matriz RACI
**Épica:** EP-001 — Definición y estrategia del producto
**Dominio:** Operating Model / Governance / Project Management
**Rol principal:** Project Manager
**Roles de apoyo:** Product Owner, Product Manager, Solution Architect, QA Lead, Knowledge Manager
**Prioridad:** P0 — Crítica
**Target:** Foundation / Pre-MVP
**Tipo de trabajo:** Gobernanza / Diseño organizacional / Procesos
**Estado:** Ready for validation
**Dependencias:** HU-001, HU-002, HU-003

---

# 2. Historia de usuario

**Como** responsable del proyecto,
**quiero** definir con precisión qué responsabilidades y capacidades tiene cada rol y cómo participan en los principales tipos de trabajo,
**para** evitar duplicidades, vacíos de responsabilidad y contradicciones entre personas, agentes y procesos automatizados.

---

# 3. Objetivo

HU-003 definió qué roles existen.

HU-004 define:

```
QUÉ HACE CADA ROL
        +
QUÉ NO HACE
        +
QUÉ PUEDE DECIDIR
        +
QUÉ DEBE REVISAR
        +
CUÁNDO PARTICIPA

```

El resultado será utilizado posteriormente para:

- asignar historias;
- diseñar agentes;
- definir permisos;
- construir workflows;
- establecer revisiones;
- crear automatizaciones;
- evitar que distintos agentes realicen trabajo contradictorio.

---

# 4. Principio de responsabilidad

Se adopta:

> **Cada decisión o entrega importante debe tener un único responsable final.**

Puede haber muchos participantes, pero solamente un accountable principal.

---

# 5. Modelo RACI

Se utilizarán cuatro tipos de participación.

## R — Responsible

Ejecuta el trabajo.

Puede haber uno o varios responsables operativos.

## A — Accountable

Tiene responsabilidad final sobre el resultado.

Debe existir exactamente uno por actividad relevante.

## C — Consulted

Debe ser consultado antes de cerrar la decisión o trabajo.

## I — Informed

Debe recibir información sobre el resultado.

### Propósito

Maximizar el valor global del producto.

### Responsabilidades

- aprobar visión;
- aprobar alcance;
- definir prioridades estratégicas;
- resolver conflictos de valor;
- aprobar cambios significativos de producto;

- prioridad estratégica;

- Product Vision;
- objetivos;

# 13. Regla para HU

Toda HU deberá contener:

```
Owner Role
Reviewer Role
Supporting Roles
RACI relevantes

```

No será necesario copiar toda la matriz.

Solamente las responsabilidades aplicables.

Ejemplo:

```
Owner: Firmware Engineer
Reviewer: QA Engineer

Support:
- Hardware Engineer
- Solution Architect

RACI:
Firmware: R
QA: A
Hardware: C
Architect: C

```

---

# 14. Regla de Accountable

Toda actividad relevante tendrá:

```
EXACTAMENTE 1 ACCOUNTABLE

```

Si una HU tiene dos Accountable, deberá corregirse antes de pasar a Ready.

---

# 15. Regla de conflictos

Cuando dos roles discrepen:

```
PRODUCT VALUE
→ Product Owner

TECHNICAL ARCHITECTURE
→ Solution Architect

QUALITY
→ QA

AGRONOMIC SAFETY
→ Agronomy Expert

PROJECT FLOW
→ Project Manager

HIGH-RISK ACTION
→ Human Owner

```

Si el conflicto cruza dominios, se registra como decisión.

---

# 16. Escalamiento de decisiones

## Nivel D1 — Local

Puede resolverlo el rol responsable.

Ejemplo:

estructura interna de una función.

## Nivel D2 — Cross-domain

Requiere consulta.

Ejemplo:

cambio en payload que impacta backend y firmware.

## Nivel D3 — Architectural

Requiere Architect y ADR.

## Nivel D4 — Strategic

Requiere Product Owner.

## Nivel D5 — Critical

Requiere aprobación humana explícita.

Ejemplos:

- riesgo eléctrico;
- compras importantes;
- producción física;
- datos sensibles;
- cambios destructivos.

# 18. Restricción de agentes

Un agente nunca obtiene más autoridad que el rol que implementa.

Ejemplo:

```
Hardware Agent
        ↓
ROLE-05 permissions
        ↓
NO puede superar A3

```

Además, la implementación técnica podrá restringir todavía más sus permisos.

---

# 19. Separación entre generación y aprobación

Cuando un agente participe:

```
AGENT
   ↓
GENERATE / EXECUTE
   ↓
REVIEWER
   ↓
APPROVAL

```

No deberá autoaprobar trabajo de alto impacto.

# 24. Regla de independencia del trabajo

Para soportar la rotación de roles:

> Una HU Ready debe contener suficiente información para poder ser retomada sin depender del contexto mental de la última sesión.

# 25. Definition of Ready por responsabilidad

Una HU no podrá ser Ready si:

- no tiene Owner;
- no tiene Accountable;
- necesita un rol consultado pero no está identificado;
- existe conflicto de ownership;
- depende de una decisión sin responsable;
- su riesgo exige aprobación no definida.

---

# 26. Definition of Done por responsabilidad

Una HU no estará Done si:

- el Responsible terminó pero el Accountable no valida cuando corresponda;
- QA requerido no revisó;
- documentación requerida no existe;
- existe una decisión pendiente;
- existen evidencias faltantes.

# 28. Gherkin

```
Feature: Gestión formal de responsabilidades del proyecto

  Scenario: Asignar una historia
    Given que existe una historia refinada
    When se prepara para pasar a Ready
    Then debe existir un rol Responsible
    And debe existir exactamente un Accountable
    And deben identificarse los roles consultados cuando corresponda

  Scenario: Detectar ownership ambiguo
    Given que una actividad tiene más de un Accountable
    When se intenta pasar la historia a Ready
    Then la historia debe permanecer en Refinement
    And debe resolverse el conflicto de responsabilidad

  Scenario: Un agente ejecuta una tarea
    Given que un agente representa un rol
    When recibe una tarea
    Then sus acciones deben permanecer dentro de la autoridad del rol
    And debe respetar los límites adicionales configurados para el agente

  Scenario: Resolver conflicto técnico
    Given que dos equipos proponen soluciones incompatibles
    And la decisión afecta arquitectura
    When el conflicto es escalado
    Then el Solution Architect debe ser Accountable de la decisión
    And debe registrarse un ADR cuando corresponda

  Scenario: Resolver conflicto de producto
    Given que existe una diferencia sobre prioridad o alcance
    When el conflicto es escalado
    Then el Product Owner debe tomar la decisión final

  Scenario: Ejecutar una acción crítica
    Given que una actividad tiene nivel de decisión D5
    When un agente o rol prepare la acción
    Then debe requerirse aprobación humana explícita
    And la acción no debe ejecutarse antes de obtenerla

  Scenario: Cambiar de disciplina
    Given que una persona termina una sesión de Hardware
    And desea continuar como Backend Engineer
    When selecciona una historia Backend en Ready
    Then la historia debe contener contexto suficiente para iniciar el trabajo
    Without requiring implicit knowledge from the Hardware session

```

# 29. Riesgos identificados

## R-014 — Roles demasiado rígidos

Un modelo excesivamente burocrático podría ralentizar a una sola persona.

**Mitigación:** RACI se aplicará de forma proporcional al riesgo.

## R-015 — Ownership ambiguo

Dos roles podrían asumir que el otro es responsable.

**Mitigación:** exactamente un Accountable.

## R-016 — Exceso de revisiones

Cada tarea podría terminar necesitando demasiados roles.

**Mitigación:** participación proporcional a impacto.

## R-017 — Agente fuera de dominio

Un agente podría actuar sobre decisiones que corresponden a otro rol.

**Mitigación:** contratos de agente basados en RACI.

## R-018 — Cuello de botella humano

Demasiadas tareas podrían requerir aprobación del propietario.

**Mitigación:** reservar D5 para decisiones realmente críticas.

# 30. Definition of Ready

HU-004 cumple DoR porque:

- HU-003 definió roles;
- existe modelo de autoridad;
- existe necesidad explícita de agentes;
- se necesita un mecanismo formal de ownership antes de automatizar.

---

# 31. Definition of Done

HU-004 podrá cerrarse cuando:

- catálogo de roles esté aceptado;
- límites de autoridad estén aceptados;
- RACI esté aprobado;
- mecanismo de escalamiento esté aprobado;
- relación rol/agente esté confirmada;
- criterios y Gherkin reflejen correctamente el modelo;
- riesgos estén registrados.

# 32. Decisiones resultantes

## DEC-019 — RACI como modelo de responsabilidad

El proyecto utilizará RACI para representar participación en actividades relevantes.

## DEC-020 — Accountable único

Toda actividad relevante deberá tener exactamente un responsable final.

## DEC-021 — Autoridad proporcional al dominio

Cada rol tendrá capacidad de decisión dentro de su especialidad y deberá escalar decisiones fuera de ella.

## DEC-022 — Niveles de decisión D1-D5

Las decisiones se clasificarán por impacto para determinar su mecanismo de aprobación.

## DEC-023 — Agentes ligados a roles

Todo agente especializado estará asociado a uno o más roles formalmente definidos.

## DEC-024 — Restricción de autoridad de agentes

Un agente no podrá disponer de más autoridad que el rol que representa.

## DEC-025 — Seguridad como responsabilidad transversal inicial

La seguridad será una capacidad transversal bajo liderazgo inicial del Solution Architect.

## DEC-026 — Compras bajo aprobación humana

Los agentes podrán investigar y recomendar adquisiciones, pero la compra permanecerá bajo aprobación humana.

## DEC-027 — Handoff obligatorio para cambios de responsabilidad

El proyecto utilizará un contrato mínimo de handoff cuando una tarea pase entre disciplinas.

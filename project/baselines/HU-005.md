# HU-005 — Diseñar la arquitectura de agentes de la empresa virtual

## 1. Información general

**ID:** HU-005
**Título:** Diseñar la arquitectura de agentes de la empresa virtual
**Épica:** EP-001 — Definición y estrategia del producto
**Dominio:** Agentic Platform / Operating Model / Architecture
**Rol principal:** Solution / IoT Architect
**Roles de apoyo:** Project Manager, Product Manager, DevOps Engineer, QA Engineer, Knowledge Manager
**Prioridad:** P0 — Crítica
**Target:** Foundation / Pre-MVP
**Tipo de trabajo:** Arquitectura / Automatización / Gobernanza / Diseño de plataforma
**Estado:** Ready for validation
**Dependencias:** HU-001, HU-002, HU-003, HU-004

---

# 2. Historia de usuario

**Como** responsable de la arquitectura del proyecto,
**quiero** definir una arquitectura formal para agentes especializados que representen los roles de la empresa virtual,
**para** automatizar trabajo repetitivo, reducir tiempos de ejecución, mantener coherencia entre disciplinas y permitir que el proyecto escale sin depender exclusivamente del trabajo manual.

---

# 3. Objetivo

La arquitectura de agentes debe permitir:

```
SOLICITUD
   ↓
IDENTIFICAR CONTEXTO
   ↓
IDENTIFICAR ROL
   ↓
SELECCIONAR AGENTE
   ↓
CARGAR CONOCIMIENTO
   ↓
EJECUTAR
   ↓
REVISAR
   ↓
APROBAR
   ↓
PERSISTIR RESULTADO

```

Los agentes no deberán funcionar como chats independientes sin contexto común.

---

# 4. Principio central

Se adopta:

> **Los agentes trabajan sobre un contexto compartido y persistente, no sobre memoria aislada de conversación.**

Por tanto, la arquitectura deberá evitar:

```
Agent A sabe algo
Agent B no lo sabe
Agent C inventa otra solución

```

y reemplazarlo por:

```
                 PROJECT KNOWLEDGE
                       │
       ┌───────────────┼───────────────┐
       ▼               ▼               ▼
   Agent A          Agent B          Agent C

```

# 6. Componentes de la arquitectura

## AGC-01 — Orchestrator

Responsable de:

- recibir solicitudes;
- interpretar intención;
- identificar dominio;
- determinar rol;
- seleccionar agente;
- construir contexto;
- controlar secuencia;
- solicitar revisión;
- dirigir resultado hacia fuente de verdad.

El Orchestrator no debe convertirse en un “agente que hace todo”.

Su función es coordinar.

---

## AGC-02 — Agent Registry

Registro donde se define:

```
agent_id
name
role
capabilities
inputs
outputs
permissions
review_requirements
tools
status
version

```

Ejemplo:

```
agent_id: AGENT-03
name: Refinement Agent
role: Project Manager / Requirements
capabilities:
  - refine_story
  - generate_gherkin
  - detect_dependencies
authority: A1

```

---

## AGC-03 — Context Builder

Responsable de construir el contexto mínimo necesario para cada tarea.

Podrá consultar:

- HU;
- épica;
- ADR;
- arquitectura;
- documentación;
- inventario;
- decisiones congeladas;
- código;
- estado del backlog;
- resultados de pruebas.

No deberá cargar todo el proyecto innecesariamente.

---

## AGC-04 — Knowledge Layer

Fuente compartida de conocimiento estructurado.

Contendrá:

```
VISION
SCOPE
DECISIONS
ARCHITECTURE
BACKLOG
INVENTORY
EXPERIMENTS
TESTS
DOCUMENTATION
LESSONS

```

Inicialmente estará basada principalmente en archivos del repositorio.

---

## AGC-05 — Execution Layer

Donde cada agente realiza su tarea.

Tipos:

```
ANALYSIS
DOCUMENT GENERATION
CODE GENERATION
REVIEW
TESTING
CLASSIFICATION
RECOMMENDATION

```

---

## AGC-06 — Review Layer

Responsable de impedir que una salida se convierta automáticamente en verdad.

Posibles revisores:

- humano;
- QA Agent;
- Architecture Agent;
- Knowledge Agent;
- rol especializado.

---

## AGC-07 — Persistence Layer

Resultado aprobado:

```
RESULT
  ↓
FILE / ISSUE / ADR / CODE / TEST / REPORT
  ↓
SOURCE OF TRUTH

```

# 7. Primera generación de agentes

Se confirma la primera generación definida previamente.

---

## AGENT-01 — Product Agent

### Rol base

Product Manager / apoyo a Product Owner.

### Objetivo

Transformar visión y necesidades en estructura de producto.

### Inputs

- Product Vision;
- Scope;
- roadmap;
- feedback;
- métricas;
- decisiones;
- product candidates.

### Outputs

- propuestas de épicas;
- features;
- objetivos;
- oportunidades;
- priorización sugerida;
- hipótesis de producto;
- análisis de alineación.

### Puede

A0–A1.

Puede analizar y preparar.

### No puede

- modificar baseline aprobada;
- aprobar alcance;
- declarar una línea comercial validada;
- cambiar prioridad estratégica sin aprobación.

---

## AGENT-02 — Project / Backlog Agent

### Rol base

Project Manager.

### Objetivo

Mantener un flujo de trabajo ejecutable.

### Inputs

- backlog;
- dependencias;
- WIP;
- bloqueos;
- prioridades;
- disponibilidad;
- roadmap.

### Outputs

- trabajo recomendado;
- backlog ordenado;
- bloqueos detectados;
- dependencias;
- métricas Kanban;
- propuestas de refinamiento.

### Caso esperado

Solicitud:

```
Tengo dos horas y quiero trabajar en backend.

```

Resultado:

```
HU-042
Priority: P1
Role: Backend
Effort: S
Status: READY
Dependencies: satisfied

```

---

## AGENT-03 — Refinement Agent

### Rol base

Project Manager / Business Analyst / QA support.

### Objetivo

Transformar una necesidad o historia candidata en una HU potencialmente ejecutable.

### Inputs

- candidate story;
- épica;
- product context;
- architecture context;
- related decisions.

### Outputs

```
Description
Value
Preconditions
Dependencies
Acceptance Criteria
Gherkin
Risks
Tasks
Tests
Evidence
DoR
DoD

```

### Restricción

Una HU generada por este agente no pasa directamente a READY.

Debe pasar por revisión correspondiente.

---

## AGENT-04 — Architecture Agent

### Rol base

Solution / IoT Architect.

### Objetivo

Mantener coherencia técnica global.

### Inputs

- architecture;
- ADR;
- HU;
- contratos;
- componentes;
- cambios propuestos.

### Outputs

- impacto técnico;
- recomendaciones;
- inconsistencias;
- propuesta ADR;
- restricciones;
- dependencias.

### Puede

A0–A1 inicialmente.

Posteriormente podrá ejecutar cambios documentales A2 bajo workflow controlado.

---

## AGENT-05 — Knowledge Agent

### Rol base

Technical Writer / Knowledge Manager.

### Objetivo

Convertir trabajo realizado en conocimiento persistente y reutilizable.

### Inputs

- conversaciones;
- HU;
- ADR;
- commits;
- experimentos;
- pruebas;
- documentación.

### Outputs

- documentación actualizada;
- índices;
- changelog;
- referencias cruzadas;
- contradicciones detectadas;
- artefactos faltantes.

### Restricción

No puede cambiar el significado de decisiones aprobadas.

# 11. Contexto mínimo

Cada tarea deberá utilizar el principio:

> **Least Context Necessary**

El agente recibe únicamente lo necesario para realizar correctamente el trabajo.

Ejemplo:

Firmware Agent no necesita cargar toda la estrategia comercial para implementar un driver.

Pero puede necesitar:

```
HU
hardware specification
protocol contract
architecture decision
test criteria

```

---

# 12. Contexto obligatorio global

Sin importar el agente, algunas reglas deberán estar siempre disponibles:

```
PROJECT BASELINES
PROJECT PRINCIPLES
ROLE AUTHORITY
SECURITY RULES
DoR / DoD
SOURCE OF TRUTH RULES

```

---

# 13. Jerarquía del contexto

Se utilizará:

```
LEVEL 0 — Immutable project rules
LEVEL 1 — Product baseline
LEVEL 2 — Architecture baseline
LEVEL 3 — Domain context
LEVEL 4 — Epic / Feature context
LEVEL 5 — HU context
LEVEL 6 — Current task

```

Los niveles superiores tienen precedencia.

---

# 14. Conflictos de contexto

Si un agente detecta:

```
HU says X
Architecture says Y

```

No debe elegir arbitrariamente.

Debe producir:

```
STATUS: BLOCKED
REASON: CONTEXT_CONFLICT

```

y escalar.

---

# 15. Memoria

Se diferencian tres tipos.

## Working Memory

Contexto temporal de una ejecución.

Se descarta o no se considera fuente de verdad después de la tarea.

---

## Project Memory

Información persistente del proyecto.

Ejemplo:

- decisiones;
- arquitectura;
- inventario;
- historias;
- experimentos.

Debe vivir en fuente de verdad.

---

## Operational Memory

Información temporal de ejecución.

Ejemplo:

- tarea en curso;
- reintentos;
- bloqueo actual;
- resultado parcial.

Puede vivir en sistema de workflow.

---

# 16. Regla de memoria

> **Un agente no puede considerar verdadero un hecho únicamente porque lo recordó de una conversación anterior.**

Debe poder relacionarlo con una fuente persistente cuando sea necesario.

# 18. Matriz de autoridad de agentes

## A0 — Read / Analyze

Permitido automáticamente.

Requiere aprobación humana.

# 32. Política de errores

Un agente deberá fallar de forma explícita.

```
FAILED

```

# 42. Gherkin

```
Feature: Arquitectura de agentes de la empresa virtual

  Scenario: Enrutar una tarea
    Given que existe una solicitud de trabajo
    When el Orchestrator analiza la solicitud
    Then debe identificar el dominio
    And debe seleccionar un agente compatible con el rol requerido
    And debe proporcionar únicamente el contexto necesario

  Scenario: Un agente necesita contexto
    Given que un agente recibe una tarea
    When necesita información del proyecto
    Then debe obtenerla desde una fuente persistente autorizada
    And no debe asumir que recuerdos de conversaciones anteriores son fuente de verdad

  Scenario: Un agente genera una salida
    Given que el agente termina su ejecución
    When la tarea requiere revisión
    Then el resultado debe pasar a Review Required
    And no debe persistirse como definitivo antes de ser aprobado

  Scenario: Existe conflicto de contexto
    Given que una HU contradice una decisión arquitectónica aprobada
    When un agente detecta la contradicción
    Then debe marcar la tarea como Blocked
    And debe reportar el conflicto
    And no debe decidir unilateralmente cuál fuente ignorar

  Scenario: Una acción es crítica
    Given que una tarea requiere autoridad A3
    When un agente prepara la acción
    Then debe solicitar aprobación humana
    And no debe ejecutarla automáticamente

  Scenario: Un agente desconoce un dato crítico
    Given que necesita información técnica para realizar una tarea
    And no existe evidencia verificable
    When intenta continuar
    Then debe reportar el dato como Unknown
    And no debe inventarlo

  Scenario: Se modifica un agente
    Given que un prompt o regla operativa cambia significativamente
    When se aprueba el cambio
    Then debe registrarse una nueva versión o cambio explícito

```

# 43. Riesgos

## R-019 — Agent Sprawl

Crear demasiados agentes difíciles de mantener.

**Mitigación:** justificar capability gap y consolidar.

## R-020 — Context Poisoning

Información incorrecta puede propagarse entre agentes.

**Mitigación:** baselines, fuentes de verdad y revisión.

## R-021 — Exceso de autonomía

Agentes con permisos innecesarios.

**Mitigación:** mínimo privilegio y A0-A3.

## R-022 — Costos operativos

Automatizaciones pueden aumentar consumo de modelos y herramientas.

**Mitigación:** métricas de costo/valor.

## R-023 — Loops entre agentes

Agentes podrían invocarse indefinidamente.

**Mitigación:** límites de workflow, estados terminales y control del Orchestrator.

## R-024 — Resultados inconsistentes

Distintas ejecuciones podrían producir decisiones diferentes.

**Mitigación:** reglas, contexto versionado, revisión y outputs estructurados.

## R-025 — Automatización de errores

Un agente puede ejecutar rápidamente una premisa incorrecta.

**Mitigación:** verificación y human-in-the-loop proporcional al riesgo.

HU-005 podrá cerrarse cuando:

- arquitectura de agentes esté aprobada;
- cinco agentes iniciales estén aprobados;
- contratos estén aprobados;
- contexto y memoria estén definidos;
- autoridad y review estén alineados con HU-003/HU-004;
- modelo de persistencia esté aprobado;
- integración conceptual con herramientas esté aceptada;
- criterios y Gherkin estén satisfechos;
- riesgos estén registrados.

# 46. Decisiones resultantes

## DEC-028 — Arquitectura multiagente coordinada

Los agentes formarán parte de una arquitectura coordinada por un Orchestrator y no operarán como chats aislados.

## DEC-029 — Contexto persistente compartido

Los agentes utilizarán información proveniente de fuentes persistentes y versionadas.

## DEC-030 — Primera generación de cinco agentes

Se mantienen como primera generación Product, Project/Backlog, Refinement, Architecture y Knowledge.

## DEC-031 — Contrato estándar de agente

Todo agente deberá trabajar bajo contratos estructurados de entrada y salida.

## DEC-032 — Contexto jerárquico

El contexto tendrá niveles de precedencia desde reglas del proyecto hasta tarea actual.

## DEC-033 — Memoria separada por propósito

Working Memory, Project Memory y Operational Memory serán conceptos separados.

## DEC-034 — Orchestrator no es agente universal

El Orchestrator coordina y enruta, pero no sustituye agentes especializados.

## DEC-035 — Least Context Necessary

Cada agente recibirá solamente el contexto requerido para su trabajo.

## DEC-036 — Minimum Privilege

Cada agente tendrá únicamente las herramientas y permisos necesarios.

## DEC-037 — Agent Versioning

Los agentes serán artefactos versionados del proyecto.

## DEC-038 — Uncertainty over invention

Ante ausencia de evidencia, los agentes deberán declarar incertidumbre en lugar de inventar información.

## DEC-039 — Review before truth

Una salida generada por agente no se convierte automáticamente en fuente de verdad cuando la tarea requiera revisión.

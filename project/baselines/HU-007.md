# 4. Definición del MVP

Para este proyecto, MVP no significa:

> producto comercial terminado.

Tampoco significa:

> sensor conectado a un ESP32.

Se define como:

> **Un prototipo técnico funcional end-to-end para un invernadero de tomate chonto capaz de capturar variables reales, almacenarlas, visualizarlas, detectar al menos una condición relevante, ejecutar o asistir una acción controlada, registrar recursos y actividades básicas y demostrar trazabilidad suficiente para comenzar a medir el comportamiento productivo del cultivo.**


---

# 6. Alcance físico del MVP

El MVP deberá operar sobre:

```
1 invernadero
+
1 cultivo
+
tomate chonto

```

No se requiere todavía:

- múltiples fincas;
- múltiples organizaciones;
- múltiples cultivos productivos;
- operación comercial SaaS.

---

# 7. Capacidades mínimas obligatorias

Se definen nueve capacidades mínimas.

## MVP-CAP-01 — Adquisición de variables reales

El sistema deberá leer variables físicas reales del invernadero mediante sensores.

Como mínimo deberá existir más de una categoría de medición.

Ejemplos:

```
AMBIENTE
+
SUELO/SUSTRATO o AGUA

```

La selección exacta de sensores será definida posteriormente a partir del inventario y relevancia agronómica.

---

## MVP-CAP-02 — Telemetría confiable

Las mediciones deberán llegar desde el dispositivo físico hasta la plataforma.

El flujo deberá permitir conocer:

```
device
sensor
variable
value
unit
timestamp
quality/status

```

---

## MVP-CAP-03 — Persistencia histórica

Las lecturas deberán almacenarse.

El usuario deberá poder consultar:

```
valor actual
+
histórico

```

No será suficiente mostrar únicamente la última lectura.

---

## MVP-CAP-04 — Dashboard operativo

Deberá existir una interfaz web mínima que permita conocer:

- estado del invernadero;
- variables actuales;
- histórico;
- estado básico de dispositivos;
- alertas relevantes.

No se requiere todavía diseño visual definitivo.

---

## MVP-CAP-05 — Detección de una condición

El sistema deberá evaluar al menos una condición relevante.

Ejemplo conceptual:

```
VARIABLE
   ↓
RULE
   ↓
NORMAL / WARNING / CRITICAL

```

La condición deberá tener fundamento agronómico o técnico documentado.

---

## MVP-CAP-06 — Acción controlada

El MVP deberá demostrar al menos una acción relacionada con un actuador.

Podrá evolucionar mediante:

```
MANUAL
   ↓
ASSISTED
   ↓
AUTOMATIC

```

No es requisito que inicialmente sea completamente autónoma.

Ejemplo candidato:

```
riego

```

La selección final se realizará posteriormente.

---

## MVP-CAP-07 — Registro de recursos

El sistema deberá demostrar que puede registrar al menos un recurso utilizado durante la operación.

Prioridad inicial:

```
agua

```

Idealmente el flujo permitirá medir o registrar:

```
cantidad
fecha
acción relacionada
cultivo/ciclo

```

---

## MVP-CAP-08 — Registro operativo

Debe ser posible registrar una actividad básica del cultivo.

Ejemplos:

- riego;
- fertilización;
- aplicación;
- mantenimiento;
- trabajo manual.

Como mínimo deberá existir:

```
actividad
fecha
duración o cantidad
tipo
observación

```

---

## MVP-CAP-09 — Trazabilidad básica

El sistema deberá poder relacionar conceptualmente:

```
CULTIVO
  ↓
MEDICIONES
  ↓
ACTIVIDADES
  ↓
RECURSOS
  ↓
EVENTOS

```

Todavía no será obligatorio calcular el costo final completo de producción.

Pero el modelo deberá permitir llegar a él posteriormente.

---

# 8. Lo que NO será obligatorio para declarar MVP

Quedan fuera como requisito obligatorio:

- detección automática de enfermedades mediante visión;
- modelos ML;
- predicción de cosecha;
- cálculo financiero completo;
- fertirriego completamente automatizado;
- control climático avanzado;
- aplicación móvil;
- multiusuario avanzado;
- multiempresa;
- comercialización;
- marketplace;
- facturación;
- hardware industrializado;
- certificaciones;
- soporte para múltiples cultivos.

Pueden desarrollarse antes si generan valor, pero no son condición para cerrar el MVP.

---

# 10. Principio Offline Resilience aplicado al MVP

Una pérdida temporal de Internet no deberá convertir el invernadero en un sistema inseguro.

Las funciones físicas esenciales deberán mantener comportamiento seguro.

No necesariamente deberán mantener toda la funcionalidad cloud.

---

# 11. Primer nodo IoT

El MVP deberá contemplar al menos:

```
1 nodo controlador funcional

```

con capacidad para:

- leer sensores;
- identificar dispositivos;
- generar timestamps o manejar tiempo;
- detectar errores;
- transmitir telemetría;
- recuperar conexión;
- exponer estado básico.

---

# 12. Calidad de datos

Una lectura no se tratará únicamente como:

```
24.5

```

Deberá incluir suficiente contexto.

Ejemplo conceptual:

```
{
  "device_id": "node-001",
  "sensor_id": "temp-001",
  "variable": "air_temperature",
  "value": 24.5,
  "unit": "C",
  "timestamp": "...",
  "quality": "valid"
}

```

El contrato final será definido posteriormente.

---

# 13. Gestión de errores

El MVP deberá demostrar al menos manejo básico de:

- sensor sin respuesta;
- lectura inválida;
- pérdida de comunicación;
- reconexión;
- servicio no disponible.

El sistema no deberá sustituir silenciosamente errores por datos aparentemente válidos.

---

# 14. Dashboard mínimo

Se requiere inicialmente:

## Vista general

Estado general.

## Variables

Valores actuales.

## Histórico

Serie temporal básica.

## Dispositivos

Estado conectado/desconectado o equivalente.

## Alertas

Condiciones detectadas.

No se requiere todavía:

- BI avanzado;
- personalización completa;
- múltiples dashboards.

---

# 15. Primera automatización candidata

Por relevancia al cultivo y alineación con optimización de recursos, la primera capacidad candidata será:

```
GESTIÓN DE RIEGO

```

Pero HU-007 no congela todavía la tecnología ni la lógica concreta del sistema de riego.

Esto se definirá después con información agronómica, hidráulica y técnica.

---

# 16. Gestión del agua

El agua deberá convertirse en uno de los primeros recursos cuantificables.

Objetivo:

```
¿Cuánta agua se utilizó?

```

Posteriormente:

```
¿Por qué?
¿Cuándo?
¿En qué cultivo?
¿Cuál fue el resultado?
¿Cuál fue su costo?

```

---

# 17. Cultivo y ciclo productivo

El sistema deberá poder representar al menos:

```
GREENHOUSE
    ↓
CROP CYCLE
    ↓
CROP
    ↓
VARIETY

```

En la primera implementación:

```
Crop = tomate
Variety/type = chonto

```

La estructura definitiva será definida dentro del modelo de dominio.

---

# 18. Trabajo humano

El MVP deberá permitir comenzar a registrar trabajo manual.

No es obligatorio automatizar su captura.

Puede empezar como:

```
Manual Entry

```

Ejemplo:

```
Actividad: poda
Duración: 2 h
Fecha: ...

```

Esto prepara el camino para costos posteriores.

---

# 19. Costos en MVP

No será requisito calcular el costo final comercial exacto.

Sí deberá demostrarse que el sistema puede almacenar componentes que posteriormente alimentarán ese cálculo.

Ejemplo:

```
agua
mano de obra
insumos
energía

```

MVP podrá comenzar con un subconjunto.

---

# 20. Alertas

Debe existir al menos un mecanismo de alerta.

Puede comenzar dentro de la aplicación.

No es obligatorio inicialmente:

- WhatsApp;
- SMS;
- correo;
- push.

Estas integraciones podrán añadirse posteriormente.

---

# 21. IA en el MVP

La IA no es requisito obligatorio para cerrar MVP.

Sin embargo, deberán empezar a recolectarse datos de forma que posteriormente puedan alimentar:

- detección de anomalías;
- recomendaciones;
- visión artificial;
- predicción.

---

# 22. Agentes internos en paralelo

El MVP del producto y la automatización interna avanzarán paralelamente.

Los cinco agentes definidos en HU-005 podrán empezar a implementarse durante la construcción del MVP.

No es requisito que todos estén totalmente automatizados para declarar funcional el prototipo agrícola.

---

# 23. Definición de éxito técnico

El MVP será técnicamente exitoso cuando pueda demostrarse de forma repetible:

```
SENSE
STORE
SHOW
ANALYZE
ACT
TRACE

```

---

# 24. Definición de éxito funcional

El usuario debe poder responder desde la plataforma, al menos parcialmente:

```
¿Qué está ocurriendo en mi invernadero?

¿Qué ocurrió anteriormente?

¿Existe alguna condición que requiera atención?

¿Qué acción se realizó?

¿Cuánto recurso se utilizó?

```

---

# 25. Definición de éxito de aprendizaje

El MVP deberá producir conocimiento suficiente para decidir:

- qué sensores aportan valor;
- qué variables son confiables;
- qué arquitectura funciona;
- qué automatizaciones generan valor;
- qué datos deben almacenarse;
- qué funcionalidades deben continuar;
- qué puede convertirse en producto comercial.

---

# 26. Definición de éxito comercial inicial

No se requiere vender todavía.

Pero al finalizar MVP deberá existir evidencia suficiente para clasificar capacidades como:

```
POTENTIAL HARDWARE PRODUCT
POTENTIAL SaaS FEATURE
POTENTIAL SERVICE
POTENTIAL DATA PRODUCT
POTENTIAL AUTOMATION PRODUCT

```

según HU-002.

---

# 27. Criterios cuantitativos iniciales

Se establecen como objetivos de ingeniería, no SLA comerciales:

### Telemetría

El sistema deberá transmitir y almacenar lecturas de forma repetible durante pruebas prolongadas.

### Datos

Las lecturas inválidas deberán poder distinguirse de las válidas.

### Histórico

Deberá existir continuidad suficiente para representar tendencias.

### Acción

La acción controlada deberá poder demostrarse varias veces sin comportamiento inesperado.

### Recuperación

Un fallo temporal de comunicación no deberá requerir necesariamente reinicio manual completo del sistema.

Los porcentajes exactos se establecerán después de caracterizar hardware y red.

---

# 28. Prueba end-to-end obligatoria

Antes de declarar MVP deberá ejecutarse una prueba que demuestre:

```
1. sensor físico obtiene lectura
2. nodo procesa lectura
3. lectura es transmitida
4. backend la recibe
5. base de datos la almacena
6. dashboard la presenta
7. una regla evalúa el dato
8. se genera evento/alerta
9. se realiza una acción autorizada
10. la acción queda registrada

```

# 32. Gherkin

```
Feature: MVP del Invernadero Inteligente

  Scenario: Capturar una variable real
    Given que existe un sensor instalado en el invernadero
    When el nodo obtiene una lectura válida
    Then debe asociarla con el sensor correspondiente
    And debe incluir una unidad
    And debe incluir una referencia temporal
    And debe transmitirla hacia la plataforma

  Scenario: Consultar información histórica
    Given que la plataforma ha recibido mediciones
    When el usuario consulta una variable
    Then debe poder visualizar su valor actual
    And debe poder visualizar mediciones históricas

  Scenario: Detectar una condición
    Given que existe una regla configurada
    And existen datos válidos
    When los datos cumplen la condición
    Then la plataforma debe generar un evento o alerta
    And debe registrar la condición detectada

  Scenario: Ejecutar una acción controlada
    Given que existe un actuador integrado
    And la acción está autorizada
    When el usuario o una regla ordena la acción
    Then el sistema debe ejecutar la acción
    And debe registrar su resultado

  Scenario: Registrar consumo de recurso
    Given que se utiliza agua durante una actividad
    When el consumo puede medirse o registrarse
    Then debe asociarse con una fecha
    And debe asociarse con el ciclo productivo cuando corresponda
    And debe permanecer disponible para análisis posterior

  Scenario: Registrar trabajo humano
    Given que una persona realiza una actividad en el cultivo
    When registra la actividad
    Then debe almacenarse el tipo de actividad
    And la fecha
    And la información cuantificable disponible

  Scenario: Ocurre una lectura inválida
    Given que un sensor produce una lectura inválida
    When el sistema procesa la medición
    Then no debe presentarla como una lectura válida
    And debe registrar su estado o error

  Scenario: Se pierde temporalmente la comunicación
    Given que el nodo pierde conectividad
    When la conectividad se restablece
    Then debe intentar recuperar su operación
    And no debe requerir necesariamente intervención manual completa

  Scenario: Validar el MVP
    Given que todas las capacidades mínimas están implementadas
    When se ejecuta la prueba end-to-end
    Then debe demostrarse adquisición
    And transmisión
    And almacenamiento
    And visualización
    And evaluación de regla
    And acción controlada
    And trazabilidad

```

# 33. Riesgos identificados

## R-032 — MVP demasiado grande

Intentar incluir toda la visión de HU-001.

**Mitigación:** capacidades mínimas explícitas.

## R-033 — MVP demasiado pequeño

Limitar el prototipo únicamente a sensores.

**Mitigación:** flujo end-to-end obligatorio.

## R-034 — Selección incorrecta de sensores

Elegir sensores poco útiles o poco confiables.

**Mitigación:** inventario + análisis agronómico + Spikes.

## R-035 — Automatización prematura

Accionar dispositivos antes de validar datos.

**Mitigación:** Manual → Assisted → Automatic.

## R-036 — Datos sin contexto

Guardar únicamente valores.

**Mitigación:** modelo de telemetría contextualizado.

## R-037 — Dashboard antes de datos

Invertir demasiado tiempo en UI sin una base real.

**Mitigación:** priorizar pipeline de datos.

## R-038 — Falta de evidencia

Considerar MVP terminado basándose en demostraciones puntuales.

**Mitigación:** pruebas repetibles y evidencias versionadas.

# 36. Decisiones resultantes

## DEC-051 — MVP end-to-end

El MVP no será únicamente un prototipo de sensores; deberá demostrar un flujo completo desde el mundo físico hasta plataforma, decisión y acción.

## DEC-052 — Tomate chonto como implementación MVP

El primer MVP operará exclusivamente sobre un invernadero de tomate chonto.

## DEC-053 — Más de una categoría de variables

El MVP deberá incorporar mediciones reales de más de una categoría relevante cuando el inventario y validación técnica lo permitan.

## DEC-054 — Histórico obligatorio

La persistencia histórica es parte del MVP.

## DEC-055 — Dashboard mínimo obligatorio

El MVP deberá disponer de visualización web de estado, valores e históricos.

## DEC-056 — Regla y alerta obligatorias

El MVP deberá demostrar al menos una condición evaluable y una alerta/evento asociado.

## DEC-057 — Acción controlada obligatoria

El MVP deberá integrar al menos una acción física controlada y trazable.

## DEC-058 — Agua como primer recurso prioritario

La medición o registro del consumo de agua será una capacidad prioritaria del MVP.

## DEC-059 — Operación humana como dato

El MVP deberá comenzar a registrar actividades humanas relevantes para permitir trazabilidad y costos futuros.

## DEC-060 — IA avanzada fuera del criterio de cierre MVP

La inteligencia artificial avanzada no será requisito para declarar exitoso el primer MVP.

## DEC-061 — Evidencia end-to-end obligatoria

No podrá declararse MVP terminado sin una prueba end-to-end documentada utilizando datos y componentes reales.

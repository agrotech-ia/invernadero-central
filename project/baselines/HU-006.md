# AgroTechIAHU-006 — Definir metodología Kanban, workflow y modelo formal del backlog

## 1. Información general

**ID:** HU-006
**Título:** Definir metodología Kanban, workflow y modelo formal del backlog
**Épica:** EP-001 — Definición y estrategia del producto
**Dominio:** Project Management / Delivery / Agentic Operations
**Rol principal:** Project Manager
**Roles de apoyo:** Product Manager, Product Owner, Solution Architect, QA Engineer, Knowledge Manager
**Prioridad:** P0 — Crítica
**Target:** Foundation / Pre-MVP
**Tipo de trabajo:** Gestión / Gobernanza / Flujo / Automatización
**Estado:** Ready for validation
**Dependencias:** HU-001, HU-002, HU-003, HU-004, HU-005

---

# 2. Historia de usuario

**Como** responsable de la ejecución del proyecto,
**quiero** definir una metodología Kanban, un workflow formal y un modelo consistente de backlog,
**para** priorizar el trabajo, limitar el trabajo simultáneo, permitir cambiar entre roles sin perder continuidad y habilitar posteriormente automatizaciones y agentes que puedan gestionar el flujo de forma segura.

---

# 3. Objetivo

El sistema de trabajo debe permitir responder de forma consistente:

```
¿Qué debemos hacer?
¿Qué tiene mayor prioridad?
¿Qué está listo?
¿Qué está bloqueado?
¿Qué depende de qué?
¿Qué rol debe ejecutarlo?
¿Cuánto trabajo está activo?
¿Qué puedo hacer ahora?
¿Qué falta para cerrar?

```

---

# 4. Metodología adoptada

Se adopta oficialmente:

**Kanban pull-based, continuo y sin sprints obligatorios.**

El proyecto trabajará sobre flujo.

No sobre compromisos artificiales de sprint.

---

# 5. Principios Kanban

## KAN-01 — Visualizar el trabajo

Todo trabajo relevante deberá estar representado.

## KAN-02 — Limitar WIP

No comenzar continuamente nuevas tareas.

## KAN-03 — Gestionar flujo

El objetivo no es mantener personas ocupadas.

Es terminar trabajo útil.

## KAN-04 — Hacer políticas explícitas

Los estados y transiciones deben tener reglas.

## KAN-05 — Mejorar continuamente

Los procesos pueden evolucionar mediante decisiones explícitas.

---

# 6. Jerarquía formal del backlog

Se establece:

```
INITIATIVE
    ↓
EPIC
    ↓
FEATURE / CAPABILITY
    ↓
USER STORY / ENABLER / SPIKE
    ↓
TASK
    ↓
SUBTASK

```

No será obligatorio utilizar todos los niveles en todos los casos.

---

Ejemplos futuros:

```

Construir prototipo técnico funcional

INI-002
Automatizar la operación interna del proyecto

INI-003
Convertir el prototipo en producto comercial

```

Horizonte:

varios meses.

---

# 8. Epic

Ejemplos:

```

EP-IOT-001

EP-WEB-001
Visualización del invernadero

EP-AGT-001

```

---

# 9. Feature / Capability

Representa una capacidad concreta.

Ejemplo:

```
FEATURE:
Monitoreo de humedad de suelo

FEATURE:
Histórico de telemetría

CAPABILITY:
Comunicación Modbus RTU

```

# 10. Tipos de trabajo

No todo deberá representarse como HU.

Se definen:

## STORY

Entrega comportamiento o valor funcional.

## ENABLER

Capacidad técnica necesaria para futuras historias.

Ejemplo:

```
Implementar bus RS485

```

## SPIKE

Investigación time-boxed.

Ejemplo:

```
Evaluar estabilidad del sensor de pH

```

## BUG

Comportamiento incorrecto respecto a lo esperado.

## TECH DEBT

Trabajo de mejora interna identificado.

## TASK

Actividad necesaria dentro de un elemento mayor.

## DOC

Trabajo puramente documental cuando tenga valor independiente.

## OPS

Actividad operativa.

## EXPERIMENT

Prueba técnica o de producto cuyo objetivo principal es obtener aprendizaje.

# 12. Workflow oficial

Se adopta inicialmente:

```
IDEA
  ↓
BACKLOG
  ↓
REFINEMENT
  ↓
READY
  ↓
IN PROGRESS
  ↓
VALIDATION
  ↓
DONE

```

Estado transversal:

```
BLOCKED

```

---

# 13. IDEA

Representa:

- oportunidad;
- necesidad;
- posible mejora;
- producto candidato;
- problema observado;
- funcionalidad aún no evaluada.

No requiere refinamiento completo.

Contenido mínimo:

```
title
short description
source
date

```

---

# 14. BACKLOG

Un elemento entra en Backlog cuando:

- tiene relación plausible con el producto;
- no ha sido descartado;
- merece evaluación futura.

No significa:

> “debe hacerse”.

---

# 15. REFINEMENT

En este estado se determina:

```
valor
alcance
rol
dependencias
criterios
riesgos
tamaño
target

```

Para historias relevantes:

- aceptación;
- Gherkin;
- DoR;
- DoD.

---

# 16. READY

READY significa:

> El trabajo podría comenzar ahora mismo sin necesitar una sesión previa de descubrimiento esencial.

Una HU Ready debe cumplir DoR.

---

# 17. IN PROGRESS

La ejecución comenzó realmente.

No se utilizará para indicar:

> “algún día quiero trabajar en esto”.

---

# 18. VALIDATION

La implementación principal está terminada pero falta validar.

Puede contener:

- testing;
- field testing;
- code review;
- architecture review;
- product acceptance;
- documentation review.

---

# 19. DONE

Significa que cumple Definition of Done.

DONE no significa únicamente:

> el código compila.

---

# 20. BLOCKED

BLOCKED será un atributo/estado transversal.

Debe registrar:

```
blocked_reason
blocking_dependency
owner
date_blocked
expected_action

```

No se moverá una tarea olvidada a Blocked sin acción asociada.

---

# 21. Transiciones permitidas

```
IDEA → BACKLOG
BACKLOG → REFINEMENT
REFINEMENT → READY
READY → IN PROGRESS
IN PROGRESS → VALIDATION
VALIDATION → DONE

```

También:

```
REFINEMENT → BACKLOG

READY → REFINEMENT

IN PROGRESS → READY

VALIDATION → IN PROGRESS

```

si se identifica retrabajo.

---

# 22. Política de WIP

Inicialmente:

```
IN PROGRESS ≤ 2

```

Validación:

```
VALIDATION ≤ 3

```

READY puede tener más elementos, pero deberá mantenerse manejable.

---

# 23. Política de inicio de trabajo

Una tercera historia no deberá comenzar si existen dos en progreso, salvo:

- una está materialmente bloqueada;
- existe trabajo de espera física;
- Project Manager documenta excepción.

---

# 24. Pull policy

El trabajo se toma desde READY.

Selección basada en:

```
Priority
Target
Dependencies
Role
Focus
Effort
Risk
Available time

```

No se seleccionará únicamente por preferencia personal.

Pero la preferencia de contexto sí podrá utilizarse entre tareas igualmente válidas.

---

# 25. Modelo de prioridad

Se establece:

## P0 — Critical

Bloquea objetivos fundamentales o mitigación crítica.

## P1 — High

Importante para el target actual.

## P2 — Medium

Valioso pero no necesario inmediatamente.

## P3 — Low

Puede esperar sin impacto relevante.

---

# 26. Regla de P0

P0 debe ser excepcional.

No más de una pequeña fracción del backlog debe estar etiquetada P0.

Si todo es P0:

> nada es P0.

---

# 30. Effort

Se utilizará:

```
XS
S
M
L
XL

```

Interpretación aproximada inicial:

```
XS
muy corto

S
una sesión

M
varias sesiones pequeñas

L
trabajo significativo

XL
debe evaluarse para división

```

No se asignarán horas rígidas como estimación contractual.

---

# 31. Regla XL

Un elemento XL no podrá pasar automáticamente a READY.

Debe existir una evaluación explícita para:

- dividir;
- justificar indivisibilidad;
- convertir parte en Spike.

---

# 32. Dependencias

Cada elemento podrá tener:

```
blocks
blocked_by
relates_to
parent
child

```

No se inventará una relación de dependencia solamente porque dos tareas sean similares.

---

# 33. Dependencia satisfecha

Una historia podrá pasar a READY si:

- sus dependencias obligatorias están Done;
- o existe evidencia de que no impiden iniciar trabajo.

---

# 34. Riesgo

Se asignará:

```
LOW
MEDIUM
HIGH
CRITICAL

```

Separado de prioridad.

Una tarea puede ser:

```
Priority P2
Risk HIGH

```

# 41. Política de refinamiento

El backlog no será refinado completamente con seis meses de anticipación.

Se usarán niveles.

```
FUTURE
low detail

NEXT
medium detail

READY SOON
high detail

READY
execution detail

```

---

# 42. Refinamiento progresivo

Esto significa que una HU futura puede contener:

```
title
problem
value
dependencies

```

mientras una HU Ready tendrá toda la información requerida.

---

# 43. Ventana de Ready

Se buscará mantener suficiente trabajo Ready para permitir cambiar de disciplina.

Objetivo inicial:

```
6–12 elementos READY

```

distribuidos entre diferentes tipos de Focus cuando sea posible.

No constituye un límite rígido.

---

# 44. Diversidad de Ready

El Project Manager buscará evitar:

```
10 historias READY
todas HARDWARE

```

Idealmente habrá opciones como:

```
Hardware
Firmware
Planning
Documentation
Backend
Testing

```

si las dependencias lo permiten.

---

# 45. Esto permitirá consultas como

```
"Quiero trabajar una hora."

"No quiero programar."

"Estoy en el invernadero."

"Solo tengo mi portátil."

"Quiero avanzar en documentación."

"Quiero trabajar hardware."

```

El Backlog Agent podrá filtrar trabajo compatible.

# 46. Política de tareas

Las Tasks no reemplazarán las historias.

Ejemplo:

```

TASK

TASK

TASK

```

El valor sigue asociado a la HU.

# 47. Regla de Subtasks

Se utilizarán únicamente cuando ayuden a ejecución.

No se descompondrá cada acción trivial.

# 52. Métricas Kanban

Se medirá progresivamente:

- Work In Progress;
- throughput;
- cycle time;
- lead time;
- blocked time;
- aging work;
- distribución por rol;
- distribución por Focus;
- retrabajo.

No se utilizarán métricas para castigar productividad.

Su objetivo es identificar cuellos de botella.

# 56. Lo que Backlog Agent no puede hacer solo

No podrá:

- cambiar baseline;
- elevar una tarea a P0 estratégicamente;
- eliminar trabajo;
- alterar alcance;
- marcar una HU como Done sin evidencia;
- ignorar WIP;
- cambiar decisiones.

# 61. Gherkin

```
Feature: Gestión Kanban del proyecto

  Scenario: Una historia pasa a Ready
    Given que una historia se encuentra en Refinement
    When cumple Definition of Ready
    And sus dependencias permiten iniciar
    Then puede pasar a Ready

  Scenario: Una historia no cumple Definition of Ready
    Given que una historia se encuentra en Refinement
    And no tiene criterios de aceptación suficientes
    When se intenta mover a Ready
    Then la transición debe rechazarse
    And la historia debe permanecer en Refinement

  Scenario: Se alcanza el límite de WIP
    Given que existen dos historias In Progress
    When se intenta iniciar una tercera
    Then debe rechazarse el inicio
    Unless exista una excepción documentada

  Scenario: Una historia queda bloqueada
    Given que una historia no puede avanzar
    When se marca como Blocked
    Then debe registrarse la causa
    And la dependencia
    And el responsable
    And la acción esperada

  Scenario: Seleccionar trabajo según contexto
    Given que existen múltiples historias Ready
    And la persona desea trabajar en documentación
    When solicita trabajo compatible
    Then deben priorizarse historias Ready con Focus Documentation
    And deben respetarse prioridad y dependencias

  Scenario: Una historia llega a Validation
    Given que la implementación principal terminó
    When existen pruebas o revisiones pendientes
    Then debe pasar a Validation
    And no debe marcarse como Done

  Scenario: Cerrar una historia
    Given que una historia está en Validation
    When satisface Definition of Done
    Then puede pasar a Done

  Scenario: Refinar trabajo futuro
    Given que una historia pertenece a un horizonte lejano
    When se registra en Backlog
    Then no debe requerirse el mismo nivel de detalle que una historia próxima a Ready

```

# 62. Riesgos

## R-026 — Backlog sobredocumentado

Intentar refinar todo desde el inicio.

**Mitigación:** refinamiento progresivo.

## R-027 — WIP falso

Mantener historias abiertas aunque no se trabaje realmente en ellas.

**Mitigación:** política estricta de In Progress.

## R-028 — Prioridades infladas

Uso excesivo de P0/P1.

**Mitigación:** criterios claros y revisión de prioridad.

## R-029 — Micromanagement

Crear demasiadas subtareas.

**Mitigación:** descomposición solo cuando ayude a ejecución.

## R-030 — Backlog desbalanceado

Tener Ready únicamente en una disciplina.

**Mitigación:** diversidad de Ready.

## R-031 — Automatización incorrecta de estados

Agentes modifican workflow sin validación.

**Mitigación:** propuesta + validación inicialmente.

---

# 63. Definition of Ready

HU-006 cumple DoR porque:

- modelo operativo está definido;
- roles y RACI están definidos;
- arquitectura de agentes está definida;
- se ha seleccionado Kanban como enfoque;
- existen necesidades claras de gestión por contexto.

---

# 64. Definition of Done

HU-006 podrá cerrarse cuando:

- workflow esté aprobado;
- WIP esté aprobado;
- jerarquía esté aprobada;
- tipos de trabajo estén aprobados;
- prioridades y targets estén definidos;
- templates estén aprobados;
- DoR/DoD estén definidos;
- políticas de dependencia y bloqueo estén aceptadas;
- Gherkin represente correctamente el flujo;
- riesgos estén registrados.

---

# 65. Decisiones resultantes

## DEC-040 — Kanban pull-based oficial

El proyecto operará mediante Kanban continuo sin sprints obligatorios.

## DEC-041 — Workflow estándar

IDEA → BACKLOG → REFINEMENT → READY → IN PROGRESS → VALIDATION → DONE será el flujo base.

## DEC-042 — Blocked transversal

Blocked representará una condición y deberá registrar causa, dependencia y acción.

## DEC-043 — Jerarquía formal

Se utilizará Initiative → Epic → Feature/Capability → Work Item → Task → Subtask.

## DEC-044 — Tipos de trabajo especializados

Story, Enabler, Spike, Experiment, Bug, Tech Debt, Doc y Ops coexistirán.

## DEC-045 — Prioridad separada de horizonte

Priority y Target serán propiedades independientes.

## DEC-046 — WIP limitado

Se mantienen límites iniciales de dos In Progress y tres Validation.

## DEC-047 — Refinamiento progresivo

El detalle requerido aumentará a medida que el trabajo se acerque a Ready.

## DEC-048 — Backlog preparado para rotación de roles

Se buscará mantener trabajo Ready en distintas disciplinas cuando las dependencias lo permitan.

## DEC-049 — Transiciones automatizadas con control

Los agentes podrán proponer cambios de estado, pero las transiciones deberán validar políticas del workflow.

## DEC-050 — Evidencia proporcional al trabajo

Definition of Done requerirá evidencia adecuada al tipo de elemento.

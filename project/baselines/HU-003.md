# HU-003 — Definir el modelo operativo de la empresa virtual

## 1. Información general

**ID:** HU-003
**Título:** Definir el modelo operativo de la empresa virtual
**Épica:** EP-001 — Definición y estrategia del producto
**Dominio:** Operating Model / Project Management / Agentic Operations
**Rol principal:** Project Manager
**Roles de apoyo:** Product Owner, Solution Architect, Technical Lead, QA Lead, Knowledge Manager
**Prioridad:** P0 — Crítica
**Target:** Foundation / Pre-MVP
**Tipo de trabajo:** Diseño organizacional / Procesos / Gobernanza / Automatización
**Estado:** Ready for validation
**Dependencias:** HU-001, HU-002

---

# 2. Historia de usuario

**Como** responsable del proyecto,
**quiero** definir un modelo operativo que represente un equipo multidisciplinario aunque inicialmente exista una sola persona ejecutora,
**para** avanzar de forma ordenada en múltiples frentes, delegar progresivamente trabajo a agentes especializados y evitar que el crecimiento del proyecto dependa de memoria, improvisación o disponibilidad de una única disciplina.

---

# 3. Contexto

El proyecto será ejecutado inicialmente por una sola persona, pero su complejidad exige responsabilidades equivalentes a las de un equipo completo.

La solución no consiste en que una persona trabaje simultáneamente como:

- Product Owner;
- Project Manager;
- ingeniero electrónico;
- desarrollador firmware;
- backend;
- frontend;
- DevOps;
- QA;
- analista de datos;
- experto agronómico;
- documentalista.

El proyecto se gestionará como una **empresa virtual basada en roles**, donde cada actividad tendrá un responsable lógico aunque la misma persona pueda asumir diferentes roles en momentos distintos.

Además, la empresa deberá automatizar progresivamente tareas repetitivas mediante agentes especializados.

---

# 4. Objetivo del modelo operativo

Crear un sistema de trabajo que permita:

```
PLANEAR
   ↓
PRIORIZAR
   ↓
ASIGNAR ROL
   ↓
EJECUTAR
   ↓
REVISAR
   ↓
VALIDAR
   ↓
DOCUMENTAR
   ↓
APRENDER

```

sin perder trazabilidad entre disciplinas.

---

# 5. Principio organizacional

Se adopta el principio:

> **Una persona puede ejecutar múltiples roles, pero una tarea debe tener un rol claramente responsable.**

Por lo tanto, el proyecto no se organizará alrededor de "cosas que debe hacer el propietario".

Se organizará alrededor de responsabilidades profesionales.

Ejemplo:

```
HU-023 — Validar comunicación RS485

Role: Firmware Engineer
Support: Hardware Engineer
Reviewer: QA Engineer

```

Aunque los tres roles sean ejecutados temporalmente por la misma persona.

# 8. Regla de responsabilidad

Toda HU deberá tener como mínimo:

```
OWNER ROLE
REVIEWER ROLE

```

Cuando corresponda:

```
SUPPORTING ROLES

```

Ejemplo:

```
HU-041

Owner: Backend Engineer
Reviewer: Solution Architect
Support: Data Engineer, QA

```

Esto permitirá que los agentes futuros sepan quién debe actuar y quién debe validar.

---

# 9. Modelo de autoridad

Se definirán cuatro niveles.

## A0 — Informar

Puede:

- analizar;
- resumir;
- detectar;
- recomendar.

No realiza cambios.

---

## A1 — Preparar

Puede generar:

- borradores;
- documentación;
- propuestas;
- Gherkin;
- casos de prueba;
- análisis.

Requiere revisión antes de ser considerado definitivo.

---

## A2 — Ejecutar reversible

Puede realizar cambios controlados y recuperables, por ejemplo:

- crear archivos;
- modificar código en branch;
- ejecutar pruebas;
- actualizar documentación;
- generar artefactos.

Debe dejar evidencia.

---

## A3 — Aprobación humana obligatoria

Aplica a:

- energización;
- control físico;
- compras;
- cambios destructivos;
- despliegues críticos;
- acceso a información sensible;
- decisiones agronómicas de alto impacto;
- cambios significativos de arquitectura.

---

# 10. Modelo humano + agentes

Los agentes no reemplazan la estructura de roles.

Los implementan.

Ejemplo:

```
ROLE
Firmware Engineer
        │
        ▼
AGENT
Firmware Agent
        │
        ▼
HU
FW-023

```

Por tanto:

```
ROLE != AGENT

```

Un rol define responsabilidad.

Un agente es una implementación automatizada o asistida de ese rol.


# 22. Handoffs

Cada entrega entre roles deberá incluir contexto suficiente.

Ejemplo:

```
Hardware Engineer
        ↓
entrega:
- diagrama
- voltajes
- pines
- protocolo
- pruebas
- restricciones
        ↓
Firmware Engineer

```

El receptor no deberá depender de revisar una conversación histórica para entender el trabajo.

---

# 23. Contrato mínimo de handoff

Todo handoff deberá responder:

```
WHAT WAS DONE?
WHY?
INPUTS?
OUTPUTS?
ASSUMPTIONS?
CONSTRAINTS?
RISKS?
OPEN QUESTIONS?
EVIDENCE?
NEXT ROLE?

```

Este contrato servirá también para comunicación entre agentes.

---

# 24. Separación de ejecución y revisión

Siempre que el riesgo lo justifique se buscará:

```
IMPLEMENTER
     !=
REVIEWER

```

En una empresa virtual ambos pueden ser la misma persona física, pero deberá realizarse el cambio de contexto.

Ejemplo:

```
Firmware Mode
implementa

↓

QA Mode
revisa

```

Los agentes futuros podrán automatizar esta separación.

# 25. Gestión de decisiones

Las decisiones importantes no deberán quedar únicamente dentro de una HU.

Se utilizarán ADR o registros equivalentes.

Ejemplo:

```
ADR-001
Uso de MQTT

ADR-002
Modelo offline-first

ADR-003
RS485 para sensores cableados

```

Las decisiones ya obtenidas en HU-001 y HU-002 serán transformadas posteriormente en registros persistentes.

# 26. Gestión de conocimiento

Se adopta el principio:

> Si una información es necesaria para ejecutar nuevamente una tarea, debe existir fuera de la memoria humana.

Esto incluye:

- pinouts;
- calibraciones;
- credenciales referenciadas de forma segura;
- procedimientos;
- configuración;
- decisiones;
- pruebas;
- resultados;
- fotografías relevantes;
- diagramas;
- versiones.

---

# 27. Automatización interna

La automatización se priorizará donde reduzca:

```
REPETICIÓN
ERRORES
CAMBIO DE CONTEXTO
TIEMPO DE DOCUMENTACIÓN
TIEMPO DE REFINAMIENTO
TRABAJO MANUAL DE SEGUIMIENTO

```

No se automatizarán procesos inestables sin antes comprenderlos.

---

# 28. Principio para agentes

Se establece:

> **Primero proceso claro, después automatización del proceso.**

Por ejemplo:

No construiremos un agente para refinar HU hasta establecer qué significa una HU correctamente refinada.

Esto evita automatizar desorden.

# 30. Cadencia operativa

No habrá sprints obligatorios.

Se establecen cuatro ciclos conceptuales.

## Plan

Revisar prioridades y riesgos.

## Execute

Tomar trabajo Ready.

## Validate

Probar y revisar resultados.

## Learn

Actualizar conocimiento y backlog.

Estos ciclos podrán ejecutarse continuamente.

# 31. Revisión periódica

Aunque se use Kanban, será necesaria una revisión periódica del sistema.

Se definirá posteriormente una cadencia para:

- backlog;
- arquitectura;
- riesgos;
- roadmap;
- costos;
- producto;
- agentes.

# 32. Reglas de escalamiento

Una tarea deberá escalarse cuando:

- contradiga arquitectura;
- implique riesgo físico;
- requiera gasto no planificado;
- altere alcance;
- introduzca dependencia crítica;
- cambie una decisión congelada;
- implique seguridad o datos sensibles;
- requiera conocimiento agronómico no disponible.

---

# 35. Definition of Done organizacional

Ninguna historia estará Done únicamente porque "funciona".

Dependiendo del tipo deberá existir:

- resultado;
- pruebas;
- evidencia;
- documentación;
- actualización de decisiones;
- ausencia de bloqueos pendientes asociados.

# 37. Gherkin

```
Feature: Operación de la empresa virtual

  Scenario: Una persona cambia de rol
    Given que existe trabajo Ready en diferentes disciplinas
    And una misma persona ejecuta varios roles
    When decide trabajar en una disciplina diferente
    Then debe poder seleccionar una historia compatible con ese rol
    And la historia debe contener suficiente contexto para ser ejecutada

  Scenario: Una historia es asignada a un rol
    Given que una historia ha sido refinada
    When pasa al estado Ready
    Then debe tener un rol responsable
    And debe indicar el rol revisor cuando corresponda

  Scenario: Un agente ejecuta una responsabilidad
    Given que existe un rol definido
    And existe un agente que implementa parte de ese rol
    When el agente recibe una tarea autorizada
    Then debe respetar las responsabilidades y límites definidos para el rol
    And debe producir evidencia del resultado

  Scenario: Una acción requiere aprobación humana
    Given que una tarea implica una acción de alto impacto
    When un agente prepare la acción
    Then no debe ejecutarla automáticamente
    And debe solicitar aprobación humana

  Scenario: Una conversación produce una decisión
    Given que una conversación con IA genera una decisión relevante
    When la decisión es aprobada
    Then debe persistirse en el repositorio
    And no debe depender únicamente del historial de conversación

  Scenario: Una historia permanece bloqueada
    Given que una historia no puede continuar
    When se identifica el bloqueo
    Then debe registrarse la causa
    And debe registrarse la dependencia
    And debe identificarse una acción de desbloqueo

  Scenario: Una historia termina
    Given que una implementación aparentemente funciona
    When se solicita moverla a Done
    Then deben verificarse sus criterios de aceptación
    And deben existir las pruebas requeridas
    And debe existir evidencia
    And debe actualizarse la documentación correspondiente

```

# 38. Riesgos

## R-008 — Sobrecarga de roles

La misma persona puede intentar mantener demasiadas historias simultáneamente.

**Mitigación:** WIP limitado y trabajo pull-based.

## R-009 — Agentes descoordinados

Múltiples agentes podrían generar soluciones contradictorias.

**Mitigación:** roles, contratos, Architecture Agent y futuro orquestador.

## R-010 — Automatización prematura

Automatizar procesos todavía no definidos.

**Mitigación:** principio "process first, automate second".

## R-011 — Pérdida de conocimiento

Resultados quedan dispersos entre conversaciones.

**Mitigación:** repositorio como fuente de verdad y Knowledge Agent.

## R-012 — Falsa independencia de roles

Una persona revisa su propio trabajo sin cambiar de perspectiva.

**Mitigación:** handoffs y separación explícita de rol de ejecución/revisión.

## R-013 — Agentes con exceso de autoridad

Un agente realiza acciones de alto impacto sin supervisión.

**Mitigación:** niveles A0–A3.

---

# 39. Definition of Ready

HU-003 cumple DoR porque:

- HU-001 define visión;
- HU-002 define alcance;
- se ha identificado la necesidad de operar como equipo virtual;
- se ha decidido incorporar agentes;
- existe suficiente información para definir responsabilidades sin implementar todavía tecnología.

---

# 40. Definition of Done

HU-003 podrá cerrarse cuando:

- roles oficiales estén aprobados;
- autoridad esté definida;
- relación rol/agente esté entendida;
- primera generación de agentes esté identificada;
- fuentes de verdad estén definidas;
- handoff mínimo esté aprobado;
- principio de rotación de roles esté aceptado;
- WIP inicial esté aceptado;
- criterios y Gherkin representen correctamente la operación;
- riesgos organizacionales estén registrados.

# 41. Decisiones resultantes

## DEC-009 — Empresa virtual basada en roles

El proyecto se gestionará como una organización multidisciplinaria aunque inicialmente una sola persona desempeñe los diferentes roles.

## DEC-010 — Responsabilidad por rol

Toda historia deberá indicar un rol responsable y, cuando aplique, rol revisor.

## DEC-011 — Roles separados de agentes

Los roles representan responsabilidades organizacionales. Los agentes son implementaciones automatizadas o asistidas de esas responsabilidades.

## DEC-012 — Primera generación de agentes

Se priorizarán Product Agent, Project/Backlog Agent, Refinement Agent, Architecture Agent y Knowledge Agent.

## DEC-013 — Human-in-the-loop por riesgo

Las acciones de alto impacto físico, económico, arquitectónico, de seguridad o de datos requerirán aprobación humana.

## DEC-014 — Repositorio como fuente de verdad

Las decisiones, arquitectura, documentación y artefactos persistentes deberán terminar en el repositorio.

## DEC-015 — Conversación no equivale a documentación

Los chats podrán utilizarse para análisis, pero una decisión relevante deberá persistirse formalmente.

## DEC-016 — Kanban pull-based

La ejecución utilizará un sistema Kanban basado en selección de trabajo Ready, sin dependencia obligatoria de sprints.

## DEC-017 — WIP inicial máximo de dos historias

Se podrán mantener hasta dos historias simultáneamente en ejecución para permitir compatibilidad con pruebas físicas o bloqueos temporales.

## DEC-018 — Process first, automate second

No se automatizará un proceso organizacional antes de definir claramente entradas, salidas, responsabilidades y criterios de calidad.

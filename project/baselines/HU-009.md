## 2. Historia

**Como** responsable de ejecutar el proyecto,  
**quiero** comparar el estado técnico real contra las capacidades del MVP, definir cómo se
verificará cada componente y convertir cada brecha en trabajo priorizado, ejecutable y trazable,  
**para** poder avanzar durante seis meses sin improvisación, alternando disciplinas y utilizando
agentes sin perder coherencia.

## 3. Regla de recuperación

No se vuelve a implementar una capacidad para la que exista evidencia suficiente de una
implementación funcional reutilizable.

`green-house/qa` representa el estado técnico recuperado relevante. La existencia de código no
implica automáticamente CALIBRATED, VALIDATED, FIELD_READY o DEPLOYED.

## 4. Modelo de madurez

AVAILABLE → ASSEMBLED → IMPLEMENTED → COMMUNICATION_TESTED → OPERATIONAL →
CALIBRATED → VALIDATED → INTEGRATED → FIELD_READY → DEPLOYED

No todos los componentes requieren todos los estados.

## 5. Principio V&V

FUNCIONA ≠ ESTÁ CALIBRADO ≠ ESTÁ VALIDADO ≠ ES SEGURO PARA AUTOMATIZAR.

Verification & Validation es un frente formal del proyecto.

## 19. Test Case estándar

Cada prueba debe incluir:
- objetivo;
- precondiciones;
- materiales;
- montaje;
- procedimiento paso a paso;
- mediciones;
- repeticiones;
- resultado esperado;
- criterio de aceptación;
- condiciones de fallo;
- evidencia;
- resultado;
- observaciones;
- follow-up;
- versión de hardware/firmware.

"Funcionó" no es evidencia suficiente.

## 20. Evidencia

Según la prueba:
CSV, logs, mensajes MQTT, fotografías, video, mediciones, screenshots, gráficas, commit,
configuración y resultados.

La prueba debe ser reproducible por otra persona técnicamente competente.

## 29. Gherkin

```gherkin
Feature: Construcción del backlog técnico y comercial del MVP

  Scenario: Existe una implementación previa funcional
    Given que existe código en el repositorio
    And existe evidencia suficiente de funcionamiento
    When se construye el backlog
    Then no debe crearse trabajo para implementar nuevamente esa capacidad
    And deben identificarse únicamente las brechas restantes

  Scenario: Un sensor funciona pero no está validado
    Given que un sensor produce lecturas
    And su comunicación funciona
    But su precisión no ha sido validada
    When se evalúa su madurez
    Then debe clasificarse como Operational
    And debe generarse trabajo de Validation

  Scenario: Una prueba requiere materiales
    Given que existe una prueba pendiente
    And requiere materiales no disponibles
    When se refina la prueba
    Then debe generarse Procurement
    And debe registrarse como dependencia

  Scenario: Ejecutar una prueba
    Given que existe un Test Case aprobado
    And están disponibles los materiales
    When se ejecuta el procedimiento
    Then deben registrarse mediciones y evidencia
    And el resultado debe ser PASS FAIL PARTIAL o NA

  Scenario: Automatizar un actuador
    Given que existe un actuador funcional
    When todavía no se ha validado su comportamiento
    Then no debe utilizarse automáticamente sobre el cultivo

  Scenario: Cambiar de disciplina
    Given que existe trabajo Ready en múltiples áreas
    When se selecciona trabajo compatible
    Then deben respetarse prioridad dependencias y WIP

  Scenario: Comunicar una ventaja
    Given que se prepara contenido público
    When se formula un claim
    Then debe clasificarse por nivel de evidencia
    And una visión o target no debe presentarse como resultado probado

  Scenario: Detectar demanda
    Given que existe una señal de mercado verificable
    When Market Intelligence la procesa
    Then debe clasificar intención segmento y posible oportunidad
    And Product Agent debe poder evaluarla como PRODUCT_CANDIDATE
```

## 31. Decisiones resultantes

### DEC-075 — V&V como frente formal
Toda capacidad crítica tendrá pruebas y evidencia reproducibles.

### DEC-076 — Pruebas y materiales son backlog
Los procedimientos, instrumentos, consumibles y compras necesarias forman parte del trabajo.

### DEC-077 — Automatización física progresiva
Bench → Manual → Logged → Assisted → Rule Control → Automatic.

### DEC-078 — Frontend real antes que rediseño visual
La integración con datos reales tiene prioridad sobre estética no bloqueante.

### DEC-079 — HU-009 como primer caso de uso multiagente
La plataforma de agentes se construye ahora y ayuda a ejecutar el resto de HU-009/MVP.

### DEC-080 — Growth comienza antes del prototipo
La construcción de audiencia, educación y aprendizaje comercial comienza durante el desarrollo.

### DEC-081 — Market Intelligence separado de Content
Demanda/intención/nichos y generación de contenido son capacidades distintas.

### DEC-082 — Publicidad como experimento
El gasto pagado será pequeño, medible y sujeto a aprobación humana.

### DEC-083 — Claims trazables
Toda afirmación pública relevante deberá vincularse a evidencia propia, externa, hecho técnico,
target o visión.

### DEC-084 — Mercado alimenta producto
Las señales de mercado pueden generar PRODUCT_CANDIDATE y trabajo de Product Discovery.

### DEC-085 — n8n como orquestación, repositorio como verdad
n8n coordina workflows; las definiciones, decisiones y artefactos persistentes viven versionados.
